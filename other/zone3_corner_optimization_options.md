# 第三区角点拟合优化方案

更新时间：2026-06-17

当前可用基线已备份：

`other/backups/zone3_corner_baseline_20260617_222335/`

包含：
- `fence_locator_node.py`
- `launch_fence.launch.py`
- `rc26_field.py`

## 当前基线

当前方案已经能粗略拟合第三区角点：

1. 上坡状态机触发点云采集。
2. 将点云转到上坡起点局部坐标。
3. 取局部 ROI。
4. 用高度分位数取平台层点。
5. 拟合外侧长边。
6. 拟合端部边；端部边不足时用正交先验补线。
7. 两条边求交得到角点。
8. 用角点和模型关键点发布 `odom -> blue_zone3_root`。

当前主要问题：

- 高度层筛选粗，容易混入人、墙、远处结构。
- 红色端部边不够稳定，fallback 会带来位置偏差。
- 角点是 2D 边界交点，不是真正 3D 角点。
- 局部坐标依赖上坡起点 yaw，车身歪几度会影响边界方向。
- 完整场地模型的方向修正和黄色预览框需要保持语义分离。

## 优化版 A：小改稳态版

目标：尽量不动整体结构，只提高稳定性。

改法：

- ROI 不变。
- 平台层高度从全局 `z_hi=86%` 改为局部高度直方图。
- 端部边 fallback 只用于显示，不参与最终 `blue_zone3_root`。
- 真实端部边需要满足：
  - 点数大于阈值。
  - 拟合残差小于阈值。
  - 与外侧边夹角接近 90 度。
  - 端部边覆盖长度大于阈值。

优点：

- 风险小。
- 保留当前能跑通的逻辑。
- 容易调参。

缺点：

- 角点仍然是 2D 交点。
- 点云遮挡严重时可能不发布最终模型。

适合：先把粗拟合变成较稳定拟合。

## 优化版 B：粗定位 + 局部 3D 二次拟合

目标：保留当前粗角点作为初值，在附近做精拟合。

流程：

1. 用当前算法得到粗角点。
2. 在粗角点附近截取小盒子：
   - XY 半径约 `0.35m ~ 0.50m`
   - Z 范围覆盖平台面、围栏、竖直边。
3. 在小盒子内分三类点：
   - 平台水平面点。
   - 外侧边/围栏边点。
   - 端部边/围栏边点。
4. 分别拟合：
   - 一个局部水平面。
   - 两条 3D 线，或两个竖直面。
5. 用两条 3D 边/竖直面的交线计算角点。
6. 用这个精角点替换粗角点发布 TF。

优点：

- 比 2D bin 边界更准。
- 能利用 Z 信息。
- 对小范围噪声更鲁棒。

缺点：

- 实现复杂度中等。
- 需要保存调试 marker：粗角点、精角点、小 ROI、两条 3D 线。

适合：当前粗拟合已经接近，想继续提升精度。

## 优化版 C：RANSAC 多线段版

目标：不依赖固定 bin 分位数，用 RANSAC 找边。

流程：

1. ROI 点云投影到 XY。
2. 用高度粗筛保留平台/围栏附近点。
3. RANSAC 找第一条长边。
4. 从剩余点中找第二条近 90 度边。
5. 两条线求交。
6. 用竖直支撑和场地尺寸先验评分。

评分条件：

- 两条边夹角接近 90 度。
- 长边长度满足预期。
- 端部边长度满足预期。
- 角点附近有竖直点列。
- 角点位置在场地模型合理范围内。

优点：

- 不太依赖车头朝向。
- 对局部斜着进入更友好。

缺点：

- 容易误选墙、人、远处边缘。
- 需要强 ROI 和高度筛选配合。

适合：车身 yaw 不稳定、点云边界比较清楚时。

## 优化版 D：模型匹配版

目标：直接把公开场地图尺寸作为先验，用点云边界匹配模型。

流程：

1. 当前角点算法只负责提供候选角点。
2. 根据模型尺寸生成多组候选位姿：
   - 角点平移。
   - yaw 小范围搜索。
   - 蓝/红侧镜像。
3. 每个候选位姿把模型边投影到点云中。
4. 计算模型边附近点数、距离残差、空缺惩罚。
5. 选择得分最高的位姿。

优点：

- 最符合“场地尺寸公开”的事实。
- 能同时利用多条边，不只依赖一个角点。
- 可输出置信度。

缺点：

- 算法量较大。
- 需要比较好的可视化调试。

适合：最终想把 `zone3_root` 做稳定发布。

## 推荐执行顺序

1. 先做优化版 A。
2. A 稳定后做优化版 B。
3. 如果车身角度影响仍明显，再做 C 或 D。

最推荐下一步：

做 B：保留当前粗角点，在粗角点附近做小 ROI 的 3D 二次拟合。

原因：

- 当前粗角点已经能靠近目标。
- 不需要推翻当前状态机和采集流程。
- 能把“粗略拟合”升级成“精角点”。

## 调试输出要求

后续每个优化版都必须保留这些 marker：

- 粗角点：红球。
- 精角点：绿色或紫色小球。
- 外侧边：蓝线。
- 端部边：红线。
- 小 ROI：半透明框或线框。
- 发布的 `blue_zone3_root`：TF 名称可见。

终端日志至少包含：

- ROI 点数。
- 平台层点数。
- 外侧边点数与 RMSE。
- 端部边点数与 RMSE。
- 两边夹角。
- 角点坐标。
- 是否使用 fallback。
- 最终是否发布 `odom -> blue_zone3_root`。
