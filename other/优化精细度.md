# 优化精细度

## 目标

让第三区蓝方场地模型能够根据雷达点云自动拟合到 `odom` 下，并尽量贴近手动 Qt 校准后的参考结果：

```text
odom -> blue_zone3_root
X = 9.8665 m
Y = 1.8655 m
Z = -0.2648 m
Yaw = 92.50 deg
```

## 2026-06-19 晚间：上坡前平台围栏早采集 + 竖直点列优先拟合

### 改动原因

实测发现：小车刚开始上坡前后，`/odin1/cloud_slam` 已经能扫到第三区平台围栏的一部分。旧逻辑等 `/uphill/state=platform` 后才开始记录点云，会丢掉这段对 RANSAC 很有价值的围栏点列；同时平台后方会出现行人、墙面、平台地面轮廓，容易把蓝线/红线带偏。

另一个问题：车斜着上坡时，状态机可能提前进入候选或确认状态。因此不能把早期状态直接当最终定位结果，只能把它当作“开始缓存点云”的信号。

### 当前策略

```text
flat_to_uphill/debug 候选稳定
  -> 开始缓存 zone3 点云
  -> 不发布 zone3 TF

uphill 确认
  -> 继续缓存

platform 确认
  -> 停止缓存
  -> 用缓存的上坡到上平台全过程点云拟合角点
  -> 发布 blue_zone3_root_auto
```

### 点云缓存修正

旧逻辑：

```text
cloud_ransac_max_points = 60000
超过上限后 pop(0)
```

问题：最早看到的平台围栏点会被后续点云挤掉。

当前逻辑：

```text
cloud_ransac_max_points = 180000
cloud_ransac_keep_first_frames = 10
超过上限时优先删除第 10 帧之后的旧帧
保留刚上坡时看到的平台围栏线索
```

### 角点拟合修正

旧逻辑容易退回：

```text
source=platform_2d_ransac:...
```

含义：主要靠平台地面投影边界找两条线。这个方法在有人、墙面、平台边缘混入时不够稳。

当前优先级：

```text
1. vertical_bins
   先找具有 Z 方向高度跨度的竖直点列
   再分 bin 提取外侧边和远端边
   最后 RANSAC + 强制 90 度正交

2. vertical_ransac
   如果 vertical_bins 不足，使用粗角点附近的竖直点列 RANSAC

3. platform_2d_ransac
   仅作为最后 fallback
```

### 后续重点

```text
1. 继续压低 platform_2d_ransac 的发布优先级
2. 对 vertical_bins / vertical_ransac 候选增加“点云应主要落在场地内侧”的几何评分
3. 对行人点云做空间剔除：远离第三区角点 ROI 的竖直点列不参与候选
4. 状态机提前发布时，fence_locator 只缓存点云，不提前发布 TF
5. 若竖直点列不足，应输出低可信调试 marker，而不是硬发布偏移模型
```

## 问题 1：完整 bag 太慢，且容易在有效片段前被暂停

最初默认从 bag 开头播放。用户实际看到日志里已经 `Pausing play`，但还没有进入上坡/上平台状态，因此没有触发第三区拟合。

处理方式：

- 在 `launch_fence.launch.py` 新增 `bag_start_offset`。
- 默认值设为 `14.0` 秒。
- 目的：跳过无关前段，但仍保留足够平地时间给状态机采集基准。

当前参数：

```text
bag_start_offset = 14.0
```

## 问题 2：bag 比节点先吐数据，状态机可能错过平地基准

调试时出现过错误现象：

```text
baseline done: z=0.421
```

这说明状态机第一次稳定采样时已经不是平地，而是接近上平台高度。此时再做坡道判断和第三区拟合，后续位置会被拖偏。

处理方式：

- launch 中让 `uphill_state_node` 和 `fence_locator` 先启动。
- bag 延迟启动。

当前参数：

```text
node_start_delay = 0.0
bag_start_delay = 2.0
```

调试结论：

- 如果看到 `baseline z≈0.42`，优先怀疑旧 bag/旧节点干扰，或者 bag 启动片段/订阅时序不对。
- 正常基准应接近：

```text
baseline done: z=-0.003, pitch=-9.34deg
```

## 问题 3：上坡围栏和行人会污染拟合

用户指出：第三区定位不应该继续使用上坡过程中的点云，因为坡道围栏会影响最终场地拟合。

处理方式：

- `fence_locator` 在 `platform` 状态之后才开始采集第三区点云。
- 上平台后缓存固定帧数点云，再一次性拟合。

当前参数：

```text
zone3_post_platform_cloud_frames = 24
```

流程：

```text
flat_to_uphill / uphill / uphill_to_platform:
  只记录坡道姿态和状态机信息

platform:
  清空旧点云缓存
  开始采集 post-platform 点云
  满 24 帧后停止采集
  使用这批点云拟合第三区角点和场地 root
```

验证日志：

```text
start post-platform point cloud collection, target_frames=24
stop post-platform point cloud collection, frames=24, samples=57987
```

## 问题 4：平台层高度筛选会被行人/竖直杂点干扰

之前平台层筛选使用 `86%` 分位高度：

```text
z_hi = percentile(z, 86)
platform = z_hi 附近的点
```

这个方法的问题：

- 行人、墙面、竖直结构可能抬高分位数。
- 平台有效点会被筛少。
- 调试中出现过：

```text
zone3 root fit: none, reason=few_platform:432
```

处理方式：

- 改成 Z 直方图最密集层。
- 平台是大面积平面，点会集中在某个 Z 高度。
- 行人和竖直结构虽然高，但高度分布更散，不容易成为最密集层。

当前逻辑：

```text
platform_z = dense_z_mode(z)
platform = platform_z - 0.12 到 platform_z + 0.16
```

当前最低平台点数门槛：

```text
min platform points = 450
```

## 问题 5：红蓝方自动判断暂时不需要

当前项目先锁定蓝方调试。用户明确表示比赛时可以手动选择红蓝方，不需要自动判断。

处理方式：

```text
field_side = blue
auto_field_side = False
forced_side = positive
```

含义：

- 角点检测只看蓝方对应的 `positive` 候选边。
- 避免自动投票选错边，导致模型跑到另一侧。

## 问题 6：两条边必须近似垂直

用户要求：用 RANSAC 拟合两条边/两个竖直面，并硬约束两个轴相互垂直。

当前实现思路：

1. 从平台点云里提取候选边界点。
2. 先用边界/bin 方法给出粗候选。
3. 再在角点附近做 RANSAC。
4. RANSAC 后不直接相信两条线的原始角度。
5. 用其中一条 RANSAC 线作为主方向。
6. 另一条边强制取垂直方向。
7. 比较两种候选：

```text
候选 A：outer 边为主，far 边垂直 outer
候选 B：far 边为主，outer 边垂直 far
```

8. 根据内点数量、跨度、RMSE 评分，选更可信的一组。

验证日志：

```text
angle=90.0deg
refined=True
source=platform_2d_ransac:orthogonal_far
outer_rmse=0.031
far_rmse=0.027
outer_inliers=1802
far_inliers=4850
```

当前现象：

- 本 bag 中 `far` 边更稳定，所以最终使用 `orthogonal_far`。
- 这表示以 far 边为主方向，再强制 outer 边垂直。

## 问题 7：点云应主要落在场地内部

用户指出：雷达点云扫到的有效边界通常来自场地内部可见面，拟合后的场地不应该让大量平台点落到围栏外。

处理方式：

- 在得到 `blue_zone3_root_auto` 后，把 post-platform 点云投到模型局部坐标系。
- 用第三区 L 形足迹判断点云在场内还是场外。
- 只在场地附近评价，避免远处墙面、行人影响评分。

蓝方当前近似足迹：

```text
主平台:
  x = [-3.0, 1.5]
  y = [-1.45, 1.15]

侧平台:
  x = [1.5, 3.05]
  y = [-1.45, 1.30]
```

当前约束：

```text
enable_zone3_inside_refine = True
zone3_inside_refine_xy_range_m = 0.08
zone3_inside_refine_xy_step_m = 0.02
zone3_inside_refine_yaw_range_deg = 0.6
zone3_inside_refine_yaw_step_deg = 0.2
zone3_inside_refine_min_outside_ratio = 0.08
zone3_inside_refine_min_outside_points = 60
```

逻辑：

- 如果场外点比例已经很低，不强行移动模型。
- 如果场外点明显偏多，才在小范围内搜索 `x/y/yaw` 微调。

验证结果：

```text
inside=7280
outside=26
out_ratio=0.00
inside_refine=(+0.000,+0.000,+0.00deg)
```

说明：

- 当前姿态已经满足场内点约束。
- 优化器没有继续移动模型，避免“越调越跑偏”。

## 当前有效判断链路

```text
状态机确认上平台
  -> 采集上平台后的点云
  -> Z 直方图找平台层
  -> 从平台层提取角点附近边界
  -> RANSAC 找两条候选边
  -> 强制两轴正交
  -> 用角点 + 正交轴推出 blue_zone3_root_auto
  -> 用场地内部点约束检查是否大量跑场外
  -> 叠加小补偿对齐 Qt 标定目标
  -> 发布 odom -> blue_zone3_root_auto
  -> Qt 可选择继续发布 odom -> blue_zone3_root
  -> rc26_field.py 让第三区模型跟随 blue_zone3_root
```

- 如果换新 bag 后行人更多，优先看：

- 当前补偿值是基于 `cha1nav2_20260523_133237` 和用户 Qt 校准结果得到的。新 bag 可以先验证，不要立刻大幅改补偿。
- 当前蓝方写死；红方后续要单独验证 `forced_side=negative` 和模型镜像。

## 2026-06-19 追加：`cha1nav2_20260523_131930` 暴露的问题

### 1. rosbag 回放链路会污染状态机判断

现象：

```text
1 倍速 + 较晚 start_offset 时，baseline 可能采到 z≈0.42m
```

这不是车真的在平地高度 0.42m，而是 WSL/rosbag 回放下消息处理延迟，状态机开始采 baseline 时车已经接近平台。此时继续调 pitch 阈值没有意义，会把回放链路问题误判成状态机问题。

处理：

```text
launch 默认 bag_rate: 1.0 -> 0.5
launch 默认 bag_start_offset: 14.0 -> 0.0
ros2 bag play 只播放必要话题:
  /odin1/odometry_highfreq
  /odin1/cloud_slam
  /tf
  /tf_static
```

实机运行不经过 rosbag 队列，这个改动主要服务于回放调试。

### 2. fence_locator 不能使用未确认的 flat_to_uphill 锁坡起点

曾经尝试让 fence_locator 同时读取 `/uphill/debug` 的 `internal_state`，结果 `flat_to_uphill` 太早触发，日志出现：

```text
ramp start fixed: x=2.801, y=4.046
zone3 root fit: none, reason=few_roi:0
```

原因：`flat_to_uphill` 只是“疑似开始上坡”，不是最终确认。fence_locator 如果在这里锁定模型，会把坡脚提前到错误位置。

当前处理：

```text
fence_locator 可以订阅 /uphill/debug
但忽略 internal_state=flat_to_uphill
只在 confirmed uphill 后使用 /uphill/transition_pose 回溯出来的坡脚
```

### 3. platform 判断已收紧

旧逻辑：

```text
pitch_abs <= 9deg -> platform
```

问题：可能仍处于坡尾或车身过渡阶段。

当前 launch 覆盖：

```text
pitch_platform_deg = 6.0
hold_s = 0.20
```

`131930` 中 platform 延后到了：

```text
pitch≈0.29deg
z≈0.427m
```

这比 9deg 触发更接近“真的上平台”。

### 4. 蓝线/角点拟合仍存在的核心问题

`131930` 在状态机修正后仍会出现：

```text
source=platform_2d_ransac:orthogonal_far
outer_rmse≈0.038
far_inliers≈6000
outer_inliers≈1000
```

含义：

- RANSAC 找到了数学上能正交的两条线。
- 但 far 边点数过多，可能混入平台轮廓、行人残留或非目标长边。
- inside/outside 比例低只能证明模型覆盖了大量点云，不能证明“这两条边就是目标角点的三边”。

已尝试但撤回：

```text
强行优先 outer/side 边作为主轴
```

结果 `131930` yaw 飘到约 119deg，比原方案更差，因此撤回。后续不能再简单按某一条边优先，需要做候选语义评分。

后续优化方向：

```text
1. 对每个 RANSAC 候选边对生成一个临时 Zone3 模型
2. 统计点云是否主要落在模型场地内侧，而不是围栏外侧
3. 对人形/墙面高点做高度和空间剔除
4. 选“内侧点最多 + 外侧点最少 + 两边都贴近围栏”的候选
5. 如果只得到低质量 platform_2d_ransac，不发布最终 TF，改为输出低置信调试 marker
```
